# P0-1 Implementation Plan — Audits must actually run (worker liveness)

Date: 2026-06-17 · **Plan only — no code in this document.**
Source finding: `plan06171210.md` › P0-1.

---

## 1. Problem

With `REDIS_URL` configured (current state), `diagnosis/start` and probe runs **enqueue
to BullMQ and never execute inline**. If the BullMQ worker (`scripts/worker.ts`,
`npm run worker`) is not running, every job stays `queued` forever:

- The customer clicks **Start Audit** → the live progress bar sits at 0% / "queued" indefinitely, with no error.
- There is **no detection** that the worker is down and **no signal** to the operator or the customer.

Evidence:
- `src/server/queue/client.ts` `enqueueAnalysisJob` adds to Redis when `isRedisConfigured()`, sets the job `queued`.
- `src/app/api/projects/[projectId]/diagnosis/start/route.ts` only runs the local in-process path when `!isRedisConfigured()`; with Redis it relies entirely on the worker.
- `src/server/diagnosis/.../start` already returns 503 in production without Redis → production **requires** Redis + a worker.
- `scripts/worker.ts` is a separate process; nothing supervises it or reports its health.

## 2. Goals / acceptance criteria

1. **Ops**: the worker runs as a supervised, auto-restarting process in every env that has Redis; documented for dev + prod.
2. **Liveness**: the system knows within ≤ ~30 s whether a live worker exists.
3. **Operator visibility**: Admin → System Health shows **Worker: up/down**, last heartbeat, and queue depth; a down worker is a visible incident.
4. **Customer honesty**: starting an audit with no live worker does **not** show a silent spinner — it shows a clear "processing is delayed / temporarily unavailable" state with the traceId, instead of implying progress.
5. **No stuck jobs**: jobs left `queued`/`running` because a worker died are detected and re-queued or failed with a clear reason.
6. **Dev ergonomics**: a local dev without a running worker still gets results (guarded inline fallback) so the product is testable.

## 3. Design

### 3.1 Worker heartbeat (liveness source of truth)
- The worker writes a heartbeat on an interval (e.g., every 10 s) and on `ready`.
- **Storage**: Redis key `cip:worker:heartbeat` → JSON `{ workerId, at, queues, pid, version }` with a TTL (e.g., 30 s) so it self-expires when the worker dies. (Redis chosen over a DB row: TTL gives automatic "down" detection and avoids DB write churn.)
- A small `worker-health.ts` module exposes:
  - `recordWorkerHeartbeat()` (called by the worker loop),
  - `getWorkerHealth()` → `{ alive: boolean, lastSeenAt, queues }` (reads the key; `alive` = key present and `at` within threshold).

### 3.2 Worker process hardening (`scripts/worker.ts`)
- Add the heartbeat interval (start on boot, clear on shutdown).
- Add graceful shutdown (SIGTERM/SIGINT → `await worker.close()` for both workers, close Redis, clear heartbeat). *(Overlaps P1-2; do together.)*
- Add `.on('error', …)` to the IORedis connection so a transient Redis error can't crash the process. *(Overlaps P2-4.)*
- Optional: set explicit `concurrency` per worker.

### 3.3 Operator visibility (`api/admin/system/health` + Admin UI)
- Extend the existing health endpoint (which already uses `checkQueueHealth()`) to also return `getWorkerHealth()` and queue depths (`queue.getJobCounts()` for the relevant queues).
- Admin → System page: a "Background processing" panel — Redis reachable (y/n), **Worker up/down + last heartbeat**, queued/active/failed counts per queue. Down worker rendered as a red incident row.

### 3.4 Customer-facing honesty (`diagnosis/start` + `AuditStatusPanel`)
- On `diagnosis/start`: after enqueue, if Redis is configured **and** no live worker heartbeat, return `202` with `executionMode: "queued_no_worker"` (job still created). Do **not** 500.
- `api/.../diagnosis/status`: include `workerAlive` (from `getWorkerHealth()`).
- `AuditStatusPanel`: when the job is `queued` **and** `workerAlive === false`, replace the progress animation with a clear state: "Your audit is queued — processing is temporarily delayed. (Trace: …)" instead of a spinner implying motion. When the worker is alive, behave as today (the live progress bar).

### 3.5 Stuck-job reconciliation
- On worker boot, reconcile: find `AnalysisJob`s in `running` with `startedAt` older than a timeout (e.g., > 30 min) whose BullMQ job no longer exists → mark `failed` with "worker restarted" or re-enqueue (configurable).
- Add a repeatable BullMQ job (or the cleanup cron from P2-3) that periodically flags `queued` jobs with no live worker as needing attention.

### 3.6 Dev inline fallback (guarded)
- In **development only**, if `isRedisConfigured()` but `getWorkerHealth().alive === false` at `diagnosis/start`, run the job inline (the existing `runLocalDiagnosisJob` path) so a solo dev sees results without `npm run worker`.
- Strictly gated: `process.env.NODE_ENV !== "production"`. Production keeps requiring a real worker (matches the existing prod guard).

## 5. Ops / deployment
- **Dev**: document `npm run worker` in a second terminal (already in README); the dev inline fallback covers the case where it isn't running.
- **Prod**: run the worker as its own supervised process — PM2 (`pm2 start npm --name cip-worker -- run worker`), a systemd unit, or a separate container/service in the deploy manifest. It must auto-restart and share `REDIS_URL` + `DATABASE_URL` + `ENCRYPTION_KEY` with the web app.
- Add a liveness probe (the heartbeat key) to monitoring/alerting.

## 6. Testing / verification
- Unit: `getWorkerHealth()` returns `alive:false` when the key is absent/expired, `alive:true` when fresh.
- Integration: start app **without** worker → `diagnosis/start` returns `queued_no_worker`; status reports `workerAlive:false`; panel shows the delayed state (not a fake spinner).
- Integration: start app **with** worker → heartbeat present; a real `deepseek-chat` audit runs to `completed`; progress bar advances through stages.
- Kill the worker mid-run → reconciler marks the in-flight job failed/re-queued; admin health flips to "down".
