## P0 — Blocks real usage, data loss, or security-critical

### P0-1. Audits stuck "queued" forever when the worker isn't running  ·  M
- **Impact (current, live):** `REDIS_URL` is set, so `diagnosis/start` and probe runs **enqueue to BullMQ and never run inline**. If `npm run worker` is not running, jobs stay `queued` indefinitely — the new live progress bar never advances, the customer sees nothing happen. This is the single highest-impact gap today.
- **Evidence:** `src/server/queue/client.ts` (`enqueueAnalysisJob` adds to Redis when configured), `src/app/api/projects/[projectId]/diagnosis/start/route.ts` (only runs local job when `!isRedisConfigured()`), `scripts/worker.ts` (must be a separate process).
- **Fix:**
  1. Run the worker as a supervised process (PM2 / systemd / container sidecar) in every env that has Redis.
  2. **Worker heartbeat**: worker writes `lastSeenAt` (Redis key or DB row); Admin → System Health shows "worker: up/down"; if down, the customer status panel shows "processing is delayed" instead of a silent spinner.
  3. Dev fallback: if no heartbeat within N seconds, allow inline execution (guarded, dev-only) so local devs without a worker still see results.

### P0-2. No environment validation at startup  ·  S
- **Impact:** Missing/weak `ENCRYPTION_KEY` or `DATABASE_URL` fails deep at runtime (provider decrypt throws, pages 500) instead of failing fast at boot. A short/empty `ENCRYPTION_KEY` is silently accepted (it's sha256-stretched), weakening key security.
- **Evidence:** `security/encryption.ts` (throws only on first use), `db.ts` (placeholder check only), no `instrumentation.ts`.
- **Fix:** Add `src/instrumentation.ts` (Next `register()`) that validates required env on boot: `DATABASE_URL` present & non-placeholder; `ENCRYPTION_KEY` length ≥ 32; in production `REDIS_URL` required (matches the diagnosis prod guard). Fail with a clear message.

### P0-3. No HTTP security headers  ·  S
- **Impact:** No HSTS, CSP, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy` → clickjacking / MIME-sniff / mixed-content exposure.
- **Evidence:** `next.config.ts` has only `redirects` + `allowedDevOrigins`.
- **Fix:** Add `headers()` to `next.config.ts` with the standard set; add a CSP (allow `'self'`, the canvas needs none special; tune `script-src`/`style-src` for Next + inline styles used by the cosmic tokens). Test the nebula/report still render under CSP.

### P0-4. No rate limiting / brute-force protection  ·  M
- **Impact:** `auth/login` & `auth/signup` accept unlimited attempts (credential stuffing); expensive AI endpoints (`diagnosis/start`, `probe-runs`, `*/generate`, `*/build`) can be hammered → cost blow-up / DoS.
- **Evidence:** `src/app/api/auth/login/route.ts` (no throttle), all generate/build routes.
- **Fix:** Redis-backed rate limiter: per-IP + per-account on auth (e.g., 5/min, lockout/backoff); per-org concurrency lock + quota on expensive endpoints (ties to P1-7).

## P1 — Production robustness / correctness

### P1-1. Job-retry idempotency  ·  M
- **Impact:** BullMQ `defaultJobOptions.attempts = 2`, so a failed `full_diagnosis` / probe / snapshot job **auto-retries**. If `runFullDiagnosis` and the snapshot builders aren't idempotent, a retry can create duplicate SamplingRuns / snapshots / double AI spend.
- **Evidence:** `queue/client.ts` (`attempts: 2`), `scripts/worker.ts`, `diagnosis-service.ts`.
- **Fix:** Make orchestration idempotent (upsert keyed by analysisJob/run id; skip stages already completed via `stageHistory`) OR set `attempts: 1` for non-idempotent job types and rely on explicit user "retry".

### P1-2. Worker graceful shutdown  ·  S
- **Impact:** No `SIGTERM`/`SIGINT` handling → on deploy/restart, in-flight jobs are killed mid-run → partial snapshots, jobs stuck `running`.
- **Evidence:** `scripts/worker.ts` (no signal handlers, no `worker.close()`).
- **Fix:** Trap signals, `await worker.close()` (let BullMQ finish/return jobs to queue), close Redis/Prisma. Add a startup reconciler that re-queues `running` jobs older than a threshold.

### P1-3. Probe prompts are hard-coded Chinese regardless of subject language  ·  ✅ DONE (2026-06-17)
> Fixed: `probe-templates.ts` (all builders, depth clauses, schema/output lines) and `seed-pool-builder.ts` (all term banks) are now bilingual and follow the subject's language (`zh-CN` → Chinese, else English). Verified with a new English-language probe test + sample output; 37 tests green.

- **Impact:** A subject with `language = "en"` (now auto-detected) still gets **Chinese probe prompts** → samples the model in the wrong language → skewed/irrelevant results for non-Chinese brands.
- **Evidence:** `src/server/brand-probes/probe-templates.ts` (all `*Base()` builders emit Chinese), `renderProbePrompt` receives `language` but doesn't use it.
- **Fix:** Localize `buildPrompt` per `language` (at minimum zh-CN/en), or keep one base language but explicitly instruct the model to answer in the subject's language. Add a test per language.

### P1-4. Migration provenance vs `migrate deploy`  ·  M
- **Impact:** Recent migrations were generated with `migrate diff --from-config-datasource` + manual `db execute` + `migrate resolve` (local DB user lacks shadow-DB/create-database perms → `migrate dev` fails P3014). Risk: a clean `prisma migrate deploy` from an empty DB may not reproduce the exact schema; `20260614120000_proof_layer/migration.sql` also contains unrelated `ALTER ... DROP DEFAULT` drift.
- **Evidence:** `prisma/migrations/2026061412/13/14*`, shadow-DB error noted during the session.
- **Fix:** On a throwaway DB, run `migrate deploy` then `prisma migrate diff --from-migrations ./prisma/migrations --to-schema-datamodel ./prisma/schema.prisma --exit-code` — must report "no diff". Grant shadow-DB perms in dev (or set `shadowDatabaseUrl`) so future migrations use the normal flow. Add this diff check to CI.

### P1-5. Prisma client not HMR/global-guarded; no pool tuning or shutdown  ·  S
- **Impact:** Module-level `let prisma` can be re-instantiated on dev HMR → Postgres connection exhaustion over a long session; no explicit pool size; no `$disconnect` on shutdown.
- **Evidence:** `src/server/db.ts`.
- **Fix:** Cache the client on `globalThis` in non-production; set `PrismaPg` pool `max`; disconnect on worker shutdown.

### P1-6. Quotas defined but only partially enforced  ·  M
- **Impact:** Plan limits exist for `auditsPerMonth`, `experiments`, `seats` but only **project creation** is gated → free/low tiers can run unlimited (expensive) audits.
- **Evidence:** `src/server/billing/usage-service.ts` (only `canCreateProject` used), `api/projects/route.ts`.
- **Fix:** Enforce `auditsPerMonth` in `diagnosis/start`, `experiments` on experiment create, `seats` on member invite. Return 402 with upgrade messaging (pattern already established).

### P1-7. No cost guardrail on AI-spend endpoints  ·  M
- **Impact:** Nothing prevents many concurrent 1000-probe runs per org → unbounded DeepSeek spend.
- **Evidence:** probe-run + diagnosis endpoints, no concurrency lock.
- **Fix:** Per-org single-active-run lock (reject/queue a second run), monthly token/cost ceiling (read `AIUsageLog`), admin-configurable.

## P2 — Reliability / quality

### P2-1. Backpressure doesn't dynamically rebuild batches  ·  M
- **Impact:** `ThroughputController` returns adjusted batch size, but `createBatches()` pre-creates all batches up front; degradation only happens via post-failure single-split, not real-time re-sizing. Under sustained 429s this is suboptimal (slower recovery).
- **Evidence:** `probe-runner.ts` (`createBatches` then `worker()` loop), `throughput-controller.ts`.
- **Fix:** Streaming batch builder — pull the next batch size from controller state at dispatch time instead of pre-building. (Batch-level 429 exponential backoff already added this session.)

### P2-2. Thin test coverage on orchestration  ·  L
- **Impact:** The 36 tests cover pure/domain logic; the end-to-end orchestration (`runFullDiagnosis`, `runBrandProbeRun`, `executeSamplingRun`, worker handlers, JSON-repair path) is untested → regressions slip through.
- **Fix:** Integration tests with a mocked provider runtime + transactional/throwaway DB: full_diagnosis happy path, probe batch 429→retry→exhaust→mark-failed, JSON repair fallback, quota rejection.

### P2-3. No retention/cleanup for `TraceEvent`, `AIUsageLog`, expired `Session`  ·  M
- **Impact:** These tables grow unbounded → slow queries, disk pressure; stale sessions linger.
- **Evidence:** no cleanup job; `recordTraceEvent` writes on nearly every op.
- **Fix:** Scheduled cleanup (worker repeatable job or external cron): delete TraceEvent/usage older than N days, expired sessions; add indexes if needed.

### P2-4. IORedis connections have no error handlers  ·  S
- **Impact:** An unhandled `'error'` event on the IORedis client can crash the process.
- **Evidence:** `queue/client.ts`, `scripts/worker.ts` (`new IORedis(...)` with no `.on('error')`).
- **Fix:** Attach `.on('error', log)` + sensible reconnect/backoff; surface Redis-down to health.

### P2-5. Build/type hygiene in CI  ·  S
- **Impact:** Stale `.next` can make local `tsc` report phantom errors against removed routes; no enforced gate.
- **Fix:** CI pipeline: `rm -rf .next && eslint && tsc --noEmit && test && next build`. Block merge on failure.

## Recommended sequencing

1. **Make audits actually run** — P0-1 (worker supervision + heartbeat + UI). Without this nothing else matters for the live product.
2. **Harden the perimeter** — P0-2 env validation, P0-3 security headers, P0-4 rate limiting.
3. **Don't double-spend / don't lose jobs** — P1-1 idempotency, P1-2 graceful shutdown, P1-7 cost guardrail, P1-6 quota enforcement.
4. **Correctness** — P1-3 probe language, P1-4 migration verification, P1-5 Prisma global.
5. **Reliability & coverage** — P2 items, then P3 polish.
